2. P0 致命问题（6 项）

定义：会导致系统被打穿、数据错乱、或直接跑不起来。面试官一旦点到，就是"项目真实性"的硬伤。

P0-1管理后台 /admin/** 完全裸奔 —— 任何人可窃取签名密钥并篡改医院数据

网关 AuthGlobalFilter.java:41-53 只拦截两类路径：/**/inner/** 和 /api/**/auth/**。所有 /admin/** 管理接口不在其中，且 7 个 admin Controller 内部也没有任何 token 校验。

// AuthGlobalFilter.java —— 只管 api，不管 admin

if(antPathMatcher.match("/api/**/auth/**", path)) { ... }     // 需登录的 api
return chain.filter(exchange);                                 // 其余一律放行

完整攻击链（三步，全部成立）：

  • ① 匿名 GET /admin/hosp/hospitalSet/findAll → HospitalSetController:33 直接 list() 返回全表，包含每家医院的 signKey 签名字段
  • ② 用拿到的 signKey 自行计算 MD5 签名（算法在 HttpRequestHelper.getSign，规则公开）
  • ③ 调用 /api/hosp/saveSchedule、/department/remove → 任意篡改、删除任意医院的科室与排班数据

顺带还能：/admin/user/lock/{userId}/{status} 冻结任意用户账号、导出全量数据字典。

面试杀伤力：★★★★★。面试官问"你的后台接口谁可以访问"，如果答"登录才能访问"就是撒谎且一查就穿。这是安全红线问题，比性能问题严重得多。

P0-5号称的"数据库乐观锁"根本不存在 —— 号源仍可超卖

ScheduleServiceImpl.java:429-446 的注释写着"原子更新号源""乐观锁"，实际实现是典型的 read-modify-write：

public void updateAvailableNumber(String hosScheduleId, Integer delta) {
    // ... delta<0 时加 available_number > 0 条件 —— 这只在 SELECT 时过滤
    Schedule schedule = baseMapper.selectOne(wrapper);      // ① 读
    if (schedule != null) {
        schedule.setAvailableNumber(schedule.getAvailableNumber() + delta);  // ② 内存改
        baseMapper.updateById(schedule);                     // ③ 写给死值，无 CAS 条件
    }
}

两个请求同时读到 10，都算出 9 并写入 → 实际只扣了 1，卖出 2 个号。真正的乐观锁应是 UPDATE schedule SET available_number = available_number - 1 WHERE available_number > 0（原子）或加 @Version 字段。

补充：全项目没有任何 @Version 字段，而 MybatisPlusConfig 却注册了 OptimisticLockerInnerInterceptor 乐观锁插件 —— 插件在空转。

面试杀伤力：★★★★★。README 把这条写成"三层防护的最后一层"。面试官问"你第三层兜底怎么实现的"→ 注释与实现不符，比没做更糟。

P0-6日志明文泄露签名密钥、身份证号、手机号、短信验证码

面试杀伤力：★★★☆☆。应届生常犯，但面试官（尤其做过金融/医疗的）会非常在意。属于"一提就懂、不提就是隐患"。

3. P1 严重问题（17 项）

定义：不致命，但都是面试官"追问一层"就会暴露的点。

P1-1Sentinel 熔断降级完全不生效

4 个 Feign Client 都配了 fallbackFactory，看起来很完整。但 service_cmn/application.properties:45 里开关是注释掉的，而且用的是旧版属性名：

#feign.sentinel.enabled=true   ← 注释状态，且是 SC 2020 的写法

Spring Cloud 2023 需要 spring.cloud.openfeign.circuitbreaker.enabled=true。当前 4 个降级类一个都不会触发，服务挂掉直接抛异常。

P1-2Sentinel 只是个依赖，没有任何流控

全项目无 @SentinelResource、无任何 FlowRule、无 dashboard 地址配置。README 写的"集成 Sentinel 流量控制，防止服务雪崩"与代码不符。

P1-3JWT 密钥默认回落到 "123456"

// JwtHelper.java:20-26
tokenSignKey = (key != null && !key.isEmpty()) ? key : "123456";

环境变量没配时，密钥就是 123456 → 攻击者可自行签发任意 userId 的 token，登录任何人账号。应该用 @Value 注入且启动强制校验，无配置直接失败。

P1-4登出是空实现，token 无法失效

// UserController.java:58-60
@PostMapping("logout")
public Result logout() { return Result.ok(); }   // 什么都不做

README 技术栈表写着"Redis：号源缓存、分布式锁、JWT 黑名单"——黑名单不存在。token 签发后 24 小时内永远有效，改密/登出都无法让它失效。

P1-5token 过期会返回 500 而不是 401

JwtHelper.getUserId 直接调用 parseClaimsJws，token 过期/被篡改会抛 ExpiredJwtException，网关和 Controller 都没有 try-catch → 全局异常处理器兜底返回 500。前端无法区分"未登录"和"服务器错误"。

P1-6医院缓存两套机制互相打架，更新删不掉缓存

// HospitalServiceImpl.java:78  写入用的是 CacheBreakdownUtil（原生 StringRedisTemplate）
cacheBreakdownUtil.getWithLogicalExpire("hospital:" + hoscode, ...)
//                                        ↑ key = hospital:1000_0

// HospitalServiceImpl.java:45  删除用的是 Spring Cache 注解
@CacheEvict(value = "hospital", key = "#hospitalSaveDTO.hoscode")
//                              ↑ 实际 key = hospital::1000_0（双冒号）

两个 key 不一样 → 医院信息更新后，用户最长 10 分钟看到的还是旧数据。

P1-7排班更新后缓存不失效

ScheduleServiceImpl.save()（第 60 行）没有 @CacheEvict，只有 remove() 加了。医院上传新排班 → getDetailSchedule 的 @Cacheable 仍返回旧排班和旧号源。

P1-8防缓存雪崩的"随机 TTL"其实所有 key 共用一个值

// RedisConfig.java  cacheManager Bean
.entryTtl(Duration.ofSeconds(600 + new java.util.Random().nextInt(180)))

这是 defaultCacheConfig()，Bean 初始化时只算一次，之后所有缓存都用同一个 TTL。注释写"过期时间 600~780 秒随机，防止缓存雪崩"，实际效果为零。正确做法是给每个 cacheName 单独配 TTL。

P1-9Spring Boot 3 里 Redis 配置前缀写错，连接池全失效

spring.redis.host=127.0.0.1
spring.redis.timeout=1800000
spring.redis.lettuce.pool.max-active=20   ← Boot 3 已改为 spring.data.redis.*

Spring Boot 3.x 已把前缀迁移到 spring.data.redis。当前配置全部不生效（碰巧默认也是 localhost:6379 所以能连上，但连接超时、连接池参数全是默认值）。

P1-10MQ 消费失败直接丢消息，无重试无死信

// OrderStatusReceiver.java
catch (Exception e) {
    channel.basicNack(tag, false, false);   // 第三参 requeue=false → 丢弃
}

且没有配置死信队列（DLX）。订单状态同步失败 = 这条状态永远丢了。应改为重试 N 次后入死信队列 + 告警。

P1-11超时未支付订单取消失败，号源永久泄漏

PaymentReconciliationTask.cancelExpiredOrders 调用 orderService.cancelOrder，但该方法开头有：

DateTime quitTime = new DateTime(orderInfo.getQuitTime());
if (quitTime.isBeforeNow()) throw new YyghException(CANCEL_ORDER_NO);

当天的号退号时间往往早于"下单后 30 分钟" → 定时任务批量取消全部抛异常 → 用户没付款，号源也没回退，白白损失一个号。

P1-12典型 N+1 查询：查一次排班列表触发几十次额外查询

// ScheduleServiceImpl.packageSchedule() —— 对每一条排班都执行：
schedule.getParam().put("hosname", hospitalService.getHospName(...));   // 一次 DB
schedule.getParam().put("depname", departmentService.getDepName(...));  // 一次 DB/Feign

返回 20 条排班 = 40+ 次额外查询。且 getHospName 每次都查库、不走缓存（缓存只在 getByHoscode 里）。应批量查询后内存映射。

P1-13Java 内存分页

getRuleSchedule 先把某科室所有日期的排班全部查出来，再 stream().skip().limit()。数据量上去后必然 OOM。应在 SQL 层分页。

P1-14MD5 签名未指定字符集 → 跨环境签名不一致

// MD5.java:17
byte[] bytes = strSrc.getBytes();   // ← 用平台默认编码

Windows 默认 GBK、Linux 默认 UTF-8。医院名、科室名是中文 → 本地签名校验通过，部署到 Linux 上全部失败。这是很经典且很难排查的坑，应显式写 StandardCharsets.UTF_8。

P1-15接口签名无防重放，且 sign 缺失时 NPE

  • 参数里有 timestamp 参与签名，但从不校验时间窗口 → 截获一次请求可永久重放
  • isSignEquals 中 sign.equals(md5Str)，请求不带 sign 时 NPE → 500
  • saveDepartment 漏了 hoscode 非空校验（其它接口都有）
  • 用 MD5 而非 HMAC-SHA256，签名强度弱

P1-16金额处理不严谨

  • 表字段 amount decimal(10,0) —— 医事服务费无法表示角分，应为 decimal(10,2)
  • order.getAmount().multiply(new BigDecimal("100")).intValue() —— 用 int 接收，金额大时溢出；应全程用 BigDecimal（分）
  • 退款时 amountReq.setTotal() 与 setRefund() 传同一个值，语义混淆

P1-17其它代码质量问题

  • 订单号可能重复：System.currentTimeMillis() + new Random().nextInt(1000000)，每次还 new Random()；虽有唯一索引兜底，但碰撞时直接抛异常而非重试
  • 查询条件写错：selectPage 里预约日期用 ge（应为 eq），传具体日期时结果不对
  • 空指针风险：getOrder 未判空直接 packOrderInfo；updateOrderStatus 对 hosRecordId.toString() 未判空；getBookingScheduleRule 中 department.getBigname() 前未判空
  • 网关用 System.out.println 打日志；解析出 userId 后没有透传给下游服务，下游只能各自再解析一遍 token
  • 全局异常处理器只 e.printStackTrace() 不打日志，HTTP 状态码恒为 200，且不区分参数校验异常
  • 大量 Map 裸用无泛型（Map payMap、IPage iPage），getBookingScheduleRule 直接返回 Object
  • 验证码用 new Random() 非安全随机；校验通过后不删除，5 分钟内可重复爆破，且无发送频率限制
  • 工具类里残留 main 方法（JwtHelper）

这是本次审核最重要的发现。README 写得非常漂亮，但多处描述与代码实际实现不符。应届生面试时，面试官就是照着你的 README/简历提问——写上去的每一条，都必须能讲出实现细节。以下 8 条会被直接问穿：

5. 真实亮点（这些可以放心讲、经得起追问）

6. 面试高频题 + 标准答法

针对这个项目，面试官大概率会问以下 10 题。给出"现在能怎么答"和"应该补到什么程度"。

Q1：你怎么防止号源超卖？
风险：如果照 README 说"三层防护"，会被追问第三层的 SQL，直接穿帮。
现在可以答（诚实版）："两层：Redisson 分布式锁保证同一排班的扣减串行化，锁内用 RAtomicLong 原子扣减号源，扣到负数就回退并抛号源不足；医院接口调用失败也会回退。数据库层目前是 select-then-update，我知道这里有竞态，正在改成 UPDATE ... SET available_number = available_number - 1 WHERE available_number > 0 的原子语句做第三层兜底。"
这样答的好处：主动承认 + 给出正确解法 = 面试官眼中的"知道自己不足且知道怎么改"，远好于被拆穿。
Q2：下单涉及多个服务，数据一致性怎么保证？
风险：当前无事务，答"用了 @Transactional"是撒谎。
现在可以答："目前这块是项目的不足：下单链路跨订单库和医院系统，本地事务管不到远程调用。我现在只做了失败补偿——号源扣减失败和医院接口失败都会回退。我了解的正确做法是：本地用 @Transactional 保证订单入库与号源扣减的原子性，跨服务部分改用可靠消息最终一致性（本地消息表 / RocketMQ 事务消息），并对医院接口做幂等。"
加分项：能说出"分布式事务为什么不用 Seata"（性能、长事务），以及"最终一致性 + 对账补偿"才是生产常用方案。
Q3：缓存穿透、击穿、雪崩你怎么处理的？
可以答（这部分是真做过的）："击穿我用逻辑过期方案：缓存存数据时附带一个逻辑过期时间戳，物理上不过期；读的时候发现逻辑过期就尝试拿 Redisson 互斥锁，拿到就重建，拿不到就返回旧数据，避免大量请求同时打到 DB。项目里 CacheBreakdownUtil 就是这个实现，医院详情接口在用。"
要补的：穿透（布隆过滤器/空值缓存）、雪崩（TTL 随机化——注意当前实现有 bug，见 P1-8）。把这三个的区别讲清楚就很加分。
Q4：为什么用 Redisson 而不是自己写 SETNX？
标准答："自己写要解决几个问题：SETNX 和 EXPIRE 不是原子的（要用 SET NX EX）、业务没执行完锁过期了怎么办、释放锁时误删别人的锁（要校验 value/UUID）、不可重入。Redisson 内置了看门狗自动续期（默认 30 秒续一次）、可重入锁、以及 RFencedLock 等，还提供了丰富的分布式对象。"
追问准备："看门狗在机器宕机时会不会死锁？"→ 不会，Redisson 实例挂了看门狗线程也停了，锁靠 Redis 的过期时间兜底释放。
Q5：微信支付回调怎么保证幂等？
风险：当前实现是先 select 判断再 update，有竞态；而且 PaymentServiceImpl 编译不过。
现在可以答："支付记录表有 out_trade_no 唯一索引，回调时先查支付记录，已支付就直接返回。不过我知道 select-then-update 在并发重试下仍有竞态。"
正确答法："更稳妥是用条件更新做幂等：UPDATE payment_info SET payment_status=PAID WHERE out_trade_no=? AND payment_status!=PAID，看影响行数是否为 1 决定是否继续后续业务；同时加分布式锁或 Redis 幂等表（SETNX 记录已处理的 out_trade_no）。"
Q6：Feign 调用失败怎么降级？
风险：fallbackFactory 当前不生效（开关注释 + 属性名过期）。
现在可以答："我给 4 个 Feign Client 都写了 FallbackFactory，返回空对象和默认值。不过我后来发现 Spring Cloud 2023 需要显式开 spring.cloud.openfeign.circuitbreaker.enabled=true 才会生效，之前用的旧属性名 feign.sentinel.enabled 已经废弃了，这是个坑，我已经改过来了。"
注意：要真的改过来再说这句话。如果没改，就说"我正在补这个配置"。
Q7：你的接口怎么保证用户不能看别人的数据？
风险：P0-2 越权 + P0-1 admin 裸奔，这个问题目前答不好。
必须这样答（先认后解）："登录态由网关的全局过滤器校验 JWT，解析出 userId。业务层的水平越权我做得还不够——订单详情和取消接口目前只校验了登录态，没有校验订单归属，订单列表虽然取了 userId 但查询条件里漏了。正确做法是每个查询都带上 userId 条件，或者用切面统一注入。管理端 /admin/** 目前网关没有拦截规则，也需要补上。"
强烈建议：这个必须真的修。安全问题是面试里"一票否决"级别的，承认了不加分，修了才加分。
Q8：项目里最难/最有挑战的点是什么？
推荐答这个（真实且可展开）："号源的高并发扣减。难点在于号源是稀缺资源，超卖会直接导致患者到院取不到号。我的方案是用 Redisson 分布式锁把同一排班的扣减串行化，配合 RAtomicLong 原子扣减，并设计了两种回退路径：扣成负数回退、医院接口调用失败回退。另外排班详情这类热点读，我用了逻辑过期 + 互斥锁防止缓存击穿。"
别选这些当"难点"：CRUD、分页、Excel 导入——太普通，撑不住追问。
Q9：RabbitMQ 消息丢了怎么办？
风险：当前消费失败直接 nack 丢弃，无死信。
现在可以答："消费者用了手动 ACK，处理成功才 basicAck。失败时目前是 nack 且不重新入队，这点我知道有问题——消息会丢。"
完整答法应该是：三层保障——① 生产者开启 publisher-confirm + return，确保消息到达交换机和队列；② 交换机/队列/消息都持久化；③ 消费者手动 ACK，失败后重试 N 次，仍失败则投递到死信队列并告警，再配合定时对账任务补偿。
Q10：你觉得项目还有哪些不足？（几乎必问）
这样答最有说服力（挑 3 个你真的理解的，不要全倒）：
"主要有三点：第一，跨服务的数据一致性目前只做了失败补偿，没有完整的最终一致性方案，我打算引入本地消息表；第二，水平越权和后台接口的鉴权做得不够细，只校验了登录态没校验数据归属；第三，排班查询有 N+1 问题，每条排班都会单独查医院名和科室名，应该改成批量查询再内存映射。"
